La question

Sirus se trompe sur environ 1 ligne sur 6.

Pour trouver ces erreurs, il faut aujourd’hui tout relire.

Un outil peut-il dire quelles lignes relire en priorité ?

Test sur la vague 1 de Budget de famille, avec les annotations comme référence.

Taux d’erreur de Sirus : 17,3 % des lignes, référence « branche » — [J] population.error_prevalence_branch. Provenance des renvois [R], [J], [D], [A], [P], [C] : annexe « D’où viennent les chiffres ».

Méthode

Les données

Une paire = un libellé, un code Sirus, un code annotateur. Toutes les paires sont jugées, sans échantillonnage.

Les codes 98/99 sont absents de la nomenclature de l’outil (détail en annexe).

Sortie reconcile-sirus du workflow du 8 septembre 2026. [J] population (n_rows, n_rows_unknown_code, n_pairs) ; [R] match_verifier_eval_summary.json (n = 8 909, n_skipped = 72 après deux échecs d’appel) ; protocole : [D] § Protocole.

La référence : le code de l’annotateur

Sirus a faux quand son code diffère de celui de l’annotateur, au niveau 4.

Exception : si Sirus est plus précis que l’annotateur, ce n’est pas une erreur.

Annotateur 03.1.2 Vêtements, Sirus 03.1.2.1 Vêtements pour hommes : correct.

[D] § Protocole ; colonnes expected_match / expected_match_branch de [R]. Définition « exacte » (sans l’exception) : annexe « Détail des chiffres ». Quand seul l’annotateur a mis un code 98/99 (341 paires), la paire est gardée et comptée comme erreur de Sirus ; résultats aussi donnés hors 98/99.

Le vérificateur

Il reçoit

  • le libellé et le code Sirus
  • la notice officielle du code
  • toute la nomenclature COICOP

Il rend

  • une note du code, sur 100
  • le meilleur code concurrent et sa note
  • un verdict

Le code est rejeté si sa note est sous 40, ou si le concurrent le dépasse d’au moins 20 points.

Modèle qwen3-6-35b-moe, raisonnement activé. Il ne sait pas que le code vient de Sirus. Il peut lire la notice d’autres codes. [P] match_verifier.py : INCOMPATIBLE_BELOW = 40, ALTERNATIVE_WINS_MARGIN = 20, SUMMARY_MAX_LEVEL = 5, enable_thinking=True ; [R] match_verifier_eval_summary.json (model, commit_sha c3e01a2).

Exemples construits pour illustrer les règles, pas des sorties réelles.

Le 2e cas est celui qu’on veut attraper. Le 3e montre la limite : sans contexte, « café » reste ambigu, et l’outil laisse passer, comme le veulent les règles. Notes fixées à la main selon [P] ; codes et intitulés réels (data/coicop_summary.txt).

Les règles de lecture

  • Marque, quantité ou prix ne changent pas le code.
  • Plusieurs articles sur une ligne : le premier cité décide.
  • Libellé ambigu : une lecture plausible suffit.
  • Une imprécision n’est pas une erreur.

Écrites par le SSP Lab. À valider avec vous.

[P] src/nomenclature.py, profil COICOP2018.reading_rules (citation abrégée).

Comment on mesure

Sirus a faux Sirus a juste
L’outil rejette erreur repérée rejet à tort
L’outil accepte erreur ratée
  • Erreurs repérées : part des erreurs de Sirus que l’outil rejette.
  • Rejets à tort : part des codes justes qu’il rejette.
  • Signalements justes : part des rejets qui sont de vraies erreurs.

Unité de compte : la paire distincte. Les signalements justes sont recalculés au taux d’erreur réel de Sirus (17,3 %), car les paires n’ont pas la même proportion d’erreurs que les lignes : précision = 0,173 × repérées / (0,173 × repérées + 0,827 × rejets à tort). src/evaluation/metrics.py (rejection_precision_at_prevalence).

La référence humaine n’est pas parfaite

Sur une quarantaine de désaccords relus à la main, environ la moitié ne sont pas des fautes de l’outil : le code Sirus était défendable, ou l’annotation était fausse.

Les chiffres présentés sont donc pessimistes.

Désaccords tirés au hasard parmi les erreurs ratées et les rejets à tort. [A] § La référence humaine est elle-même bruitée. L’échantillon relu n’est pas archivé : résultat non reproductible en l’état. Voir aussi l’annexe « Même libellé, même code ? ».

Message : quand les deux signalent, 2 lignes sur 3 sont de vraies erreurs ; attraper 75 % des erreurs demande de relire un tiers des lignes.

Limites

Ce que ces résultats ne disent pas

  • Un seul essai, un seul modèle, une seule vague.
  • La référence humaine contient des erreurs.
  • L’outil a des défauts connus, à corriger.
  • 20 secondes par libellé : en différé, pas en temps réel.

Pas de mesure de variabilité d’un run à l’autre. Les ± sont une approximation binomiale qui ignore le regroupement en paires. Défauts : l’alternative reprend le code jugé dans 7,5 % des paires, n’en est qu’un sous-code dans 21 % ; 88 paires acceptées malgré un concurrent à +20 points ([A] § Défauts, recalculés [C]). Coût : 49 h de calcul, 10 h en temps réel avec 5 appels en parallèle ([R] total_duration_s = 177 238 s).

Ce qu’on en retient

Usage proposé

  • Pas de correction automatique : 4 signalements sur 10 portent sur un code correct.
  • Relire d’abord les lignes signalées, surtout par les deux modèles.
  • Montrer le code proposé à l’annotateur, qui tranche.

Aussi : repérer des annotations douteuses dans l’historique. [A] § Recommandations.

Ce dont nous avons besoin

  1. Arbitrer quelques centaines de désaccords dans l’application de revue.
  2. Relire les règles de lecture : restauration, santé, marques.
  3. Nous dire où ce signal serait utile dans la chaîne de reprise.

Application de revue : src/evaluation/apps/match_verifier_eval_app.py. L’arbitrage dira ce que vaut réellement l’outil et corrigera des annotations au passage.

Ensuite, côté SSP Lab

  • Corriger les défauts de l’outil.
  • Intégrer vos règles de lecture.
  • Relancer l’évaluation sur les mêmes données.

  --code-column sirus_code --expected-code-column code_lvl4 \
