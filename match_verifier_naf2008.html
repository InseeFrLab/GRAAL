Contexte

Le MatchVerifier reçoit un libellé et un code, lit la notice du code dans le graphe Neo4j et rend un verdict : le code tient-il ? Il propose aussi, à chaque fois, le meilleur code concurrent. Utilisé derrière un classifieur, il sert à repérer les codes à renvoyer en reprise manuelle.

Cette page transpose à la NAF rév. 2 l’évaluation menée sur la COICOP : on lui soumet les codes APE attribués en production (par règles ou par le modèle fastText) et on compare son verdict à l’annotation humaine des mêmes liasses.

Protocole

  • Données : jeu de test de la campagne d’annotation 2024 (NAF 2008), joint par numéro de liasse aux exports Label Studio pour retrouver le code attribué en production.
  • Code jugé : apet_finale, code de production, attribué soit par règles (AUTO), soit par le modèle (FASTTEXT). Référence : apet_manual, code retenu par l’annotateur. Les deux au niveau sous-classe.
  • Graphe : NAF rév. 2 construite depuis les notes explicatives Insee, dans une instance Neo4j dédiée ; profil de nomenclature naf2008. Tous les codes du jeu y figurent.
  • Paires : les doublons (libellé, code de production, code humain) ne sont jugés qu’une fois. Toutes les paires sont évaluées, sans échantillonnage.
  • Erreur : production ≠ humain. Le vérificateur détecte une erreur quand il rejette le code.
  • Deux vérités :
    • exacte : même sous-classe ;
    • de classe : mêmes 4 premiers caractères. Un écart de sous-classe (68.20A / 68.20B) n’y compte pas comme une erreur. Elle remplace la vérité « de branche » de la COICOP, sans objet ici puisque les deux codes sont toujours des sous-classes.
  • Modèle : qwen3-6-35b-moe, prompt du commit b753427.

Choisir un seuil sur p_match

Le verdict is_match n’est qu’un point de fonctionnement. p_match, la probabilité du verdict lue dans le modèle, permet en principe d’en choisir un autre sans relancer : rejeter dès que p_match < t. La courbe montre, pour chaque seuil, la part d’erreurs détectées contre la part de codes justes rejetés (vérité exacte).

Analyse

md`Run terminé le 17 novembre 2026 : ${data.n_done.toLocaleString("fr-FR")} paires jugées, ${data.n_total - data.n_done} abandonnées (réponse du modèle tronquée). Ce que disent les chiffres

  • Le vérificateur détecte une erreur de la production sur deux (51 % en vérité exacte, 53 % en vérité de classe), comme en COICOP. Mais il rejette 16,6 % des codes justes, plus du double de la COICOP (7,6 %). Pondéré par le nombre de lignes plutôt que par paire distincte, le rappel reste à 52 % et les rejets à tort tombent à 14 %.
  • Plus d’un rejet sur deux porte sur un code juste au taux d’erreur réel de la production (précision du rejet : 44 %). Envoyer en reprise tout ce qu’il rejette ferait revoir environ un quart des paires pour y trouver la moitié des erreurs.
  • Quand il rejette à raison, il corrige une fois sur trois : son alternative est le code humain dans 36 % des cas, contre 52 % en COICOP.
  • Il voit mieux les erreurs grossières (58 % de rejet quand la section diffère, 57 % pour une autre division de la même section) que les confusions entre sous-classes voisines (36 %).
  • Le comportement diffère fortement selon le mode d’attribution :
    • sur les codes AUTO (règles, 10 % d’erreurs), il détecte 41 % des erreurs pour 9,8 % de rejets à tort ; à ce faible taux d’erreur, deux rejets sur trois portent sur un code juste ;
    • sur les codes FASTTEXT (modèle, 41 % d’erreurs), il détecte 55 % des erreurs mais rejette un tiers des codes justes (32 %), et son AUC tombe à 0,63. Ces libellés, que les règles n’ont pas su coder, sont aussi plus difficiles pour lui.

p_match ne sert pas à choisir un seuil

Comme en COICOP, et plus nettement encore, p_match est binaire : la quasi-totalité des paires sont sous 0,1 ou au-dessus de 0,9, et les seuils de 0,1 à 0,9 donnent tous exactement le même point (51,0 % d’erreurs détectées, 16,6 % de rejets à tort). Le seul point de fonctionnement réel est le verdict actuel ; les rejets à tort se font avec p_match ≈ 0, donc hors de portée d’un seuil.

D’où viennent les rejets à tort

Ils sont très concentrés : cinq codes en portent 43 %.

Code Intitulé Rejets à tort Part des codes justes rejetés
68.20B Location de terrains et d’autres biens immobiliers 173 32 %
81.21Z Nettoyage courant des bâtiments 72 43 %
96.09Z Autres services personnels n.c.a. 50 30 %
66.30Z Gestion de fonds 45 90 %
47.91B Vente à distance sur catalogue spécialisé 30 37 %

Le modèle lit la note explicative à la lettre là où les annotateurs appliquent des conventions de codage absentes des notes : une SCI va en 68.20B, un « homme toutes mains » en 81.21Z, une conciergerie en 96.09Z. Beaucoup de libellés sont en outre des objets sociaux juridiques et multi-activités, où le vérificateur trouve toujours une activité mieux placée ailleurs.

Défauts du vérificateur repérés

Ceux relevés en COICOP sont ici marginaux : l’alternative reprend le code jugé dans 1 % des paires seulement (7,5 % en COICOP), et le verdict contredit ses propres scores dans 22 paires (0,3 %).

Recommandations

  1. Ne pas utiliser le verdict seul pour router vers la reprise manuelle : avec une précision de 44 %, et un tiers des codes justes rejetés sur la part FASTTEXT, il ferait revoir beaucoup de codes justes. Il peut au mieux prioriser la reprise.
  2. Injecter des précédents annotés dans le prompt : les libellés annotés les plus proches avec leur code humain, pour faire entrer les conventions de codage que les notes ne disent pas. Les exports Label Studio NAF 2008 en contiennent environ 19 000 hors jeu de test. Mesurer l’effet sur les rejets à tort sans dégrader le rappel.
  3. Traiter à part les quelques codes qui concentrent les rejets (68.20B, 81.21Z, 96.09Z, 66.30Z), par des règles de lecture explicites dans le profil naf2008.
  4. Faire arbitrer un échantillon des désaccords par un annotateur, comme recommandé pour la COICOP : une part des rejets « à tort » peut venir de l’annotation.
